# PR Patterns: firecrawl/firecrawl

## Corpus
- PRs analyzed: 5 (numbers: #4442, #4444, #4445, #4446, #4448)
- Caveat: 3 of 5 PRs are by the same author (developersdigest), and all were merged within a single ~16-hour window (2026-08-28 14:05 → 2026-08-29 06:09 UTC). More importantly, 4 of 5 descriptions are 100% auto-generated by the `cubic` review bot with zero human text. This sample reflects an automated description pipeline, not a human writing culture; it is too small and bot-dominated to draw conclusions about how firecrawl contributors write descriptions when left to themselves.

## Titles
Titles mostly follow Conventional Commits with compound, deeply-nested scopes; one outlier:
- `Exchange/applications proxy` (#4442) — plain phrase, no type prefix, title-case path
- `feat(api/scrapeURL/formats/json): support ZDR` (#4444) — four-level slash-nested scope
- `feat(exchange): proxy more routes` (#4445) — simple scope
- `feat(exchange): proxy more routes` (#4446) — **exact duplicate title of #4445** (merged 2 hours later)
- `fix(api): missing serde error` (#4448)

Pattern: `type(scope>): <lowercase imperative>` in 4 of 5; types observed are only `feat` and `fix`. Lengths ~20–45 chars, single line, no emoji, no trailing period. The duplicate title (#4445/#4446) suggests speed-over-polish iteration on a route-by-route proxy rollout.

## Description structure
Human-authored structure is essentially absent. Per PR:

- PR #4442: empty human body; then `## Summary by cubic` (H2) with one prose paragraph
- PR #4444: the only human text in the corpus — two short declarative sentences ("ZDR deny policy on JSON mode has been lightened to only disallow json.agent/smart scrape (which is deprecated). / We must only use models in the JSON mode flow which we have ZDR agreements with going forward."), then a `---` divider, then `## Summary by cubic` with a paragraph plus 2 bullets
- PR #4445: `## Summary by cubic` — paragraph + 2 bullets
- PR #4446: `## Summary by cubic` — paragraph + 3 bullets
- PR #4448: `## Summary by cubic` — one paragraph, no bullets

Canonical order: [rare human preamble] → `---` (only when human text exists) → bot block (`## Summary by cubic` → paragraph → optional bullets → commit-hash footer → "Review in cubic" badge). No human-invented section headers (no "What changed"/"Testing"/"Motivation") appear anywhere.

## Template usage
No repo PR template is in evidence for human authors: no checklists (`- [ ]`), no "How Has This Been Tested" scaffold, no unfilled prompts — human text is either absent entirely (4 of 5) or two freehand sentences (#4444). However, the cubic block itself functions as an enforced mechanical template: identical `<!-- This is an auto-generated description by cubic. -->` opener, `## Summary by cubic` header, `<sup>Written for commit <sha>. Summary will update on new commits.</sup>` footer, and an HTML badge link appear verbatim in all 5 PRs. Conclusion: **no human template; an externally-imposed bot template dominates**.

## Length & density
Extremely short. Human-written content per PR: #4442 = 0 words, #4444 = ~45 words, #4445 = 0, #4446 = 0, #4448 = 0. Including bot text, total bodies run ~60–110 words. Change sizes are tiny (+2 to +48 additions, 1–3 files), and the description density matches: this is a fast-iteration, small-diff workflow where the description is a generated courtesy, not an authored artifact.

## Voice & tone
- Human sample is one PR, but instructive: #4444 uses declarative/explanatory prose with first-person plural in a normative statement ("We must only use models…"), present tense, informal-technical register, no greeting or sign-off, and an inline parenthetical aside ("(which is deprecated)").
- The bot voice (4 of 5) is uniform third-person imperative-ish summary: "Adds a proxy for…", "Relaxes Zero Data Retention (ZDR) restrictions…", "Fixes missing serialization for…", with bulleted implementation facts underneath.
- No emoji, no humor, no reviewer-directed pleasantry anywhere.

## Content habits
- **Linked issues**: none — zero "Fixes #N"/"Closes #N" across all 5 PRs, and zero linked issues in the metadata.
- **Test plans**: none. No validation commands, no test counts, no QA notes in any description.
- **Screenshots/images**: none (expected — all 5 are backend route/serialization changes).
- **Breaking-change callouts**: none, though #4444 changes ZDR policy behavior without flagging it as breaking.
- **Labels**: none on any PR. **Reviews**: light but present — every PR has ≥1 review; #4444 has 2 reviews / 2 comments. Review happens in the review thread, not the description.
- **Speed signal**: median create→merge latency is ~20 minutes (#4442: 20 min, #4444: 18 min, #4448: ~1 min), consistent with descriptions being treated as low-value boilerplate.

## Bot-generated content
This repo is a maximal example of bot-generated descriptions: `cubic` (cubic.dev) wrote 4 of 5 descriptions end-to-end and appended itself to the fifth. Every block follows the same contract — an HTML comment marker, a `## Summary by cubic` H2, a summary paragraph ("Adds a proxy for `/exchange/applications` so applicants can become providers without the `exchangeRetrieve` flag."), optional bullets ("- Proxies `POST` and `GET /rates/lookup` through the existing exchange proxy."), a `<sup>Written for commit <sha>…</sup>` self-updating footer, and a dark/light-mode "Review in cubic" badge image. Maintainers keep the bot block intact — it is never edited out or trimmed, and in 4 cases it is the *entire* description, meaning the bot output was accepted as merge-ready with no human additions. This is a direct, successful displacement of human/AI-assisted description writing by a review-tool-generated summary.

## Notable exemplars
- **PR #4444** — https://github.com/firecrawl/firecrawl/pull/4444 — the only sample with human intent: two sentences capture *why* the change exists and the policy constraint behind it ("We must only use models in the JSON mode flow which we have ZDR agreements with going forward."), which the bot summary alone would not have conveyed.
- **PR #4442** — https://github.com/firecrawl/firecrawl/pull/4442 — the best pure-bot description: a single paragraph that explains both the mechanism and the motivation ("applicants who aren't yet customers, so requiring the flag would block them"), showing the quality ceiling of the cubic summaries.
